# V0.4 输入链路诊断记录

日期：2026-10-16  
目的：判断识别偏差主要来自实时输入与保存回放之间的差别，还是模型本身的识别能力。

## 已有对照样本

| 项目 | 内容 |
|---|---|
| 原句 | 我觉得现在的识别结果不准确 |
| 实时识别 | 我对的现在的边界观不过是说的对 |
| 从已保存嘴部 MP4 重新识别 | 我对的现在的偏见广播说的对 |
| 模型 | `model_avg_cncvs_2_3_cnvsrc.pth`（CNVSRC） |
| 模型输入帧数 | 206 |
| 实时识别字符错误率（CER） | 11/13，约 84.6% |
| MP4 回放识别 CER | 9/13，约 69.2% |

CER 是把识别结果改成原句所需的最少字符增删改数量，再除以原句字符数；数值越低越接近原句。这里的 13 个字符按原句去除空格后计数。

## 当前能得出的结论

同一段已保存 MP4 连续离线识别 3 次，输出一致，说明“MP4 文件 → CNVSRC 推理”这一路可重复。实时结果和 MP4 回放结果不同，说明实时推理用的嘴部帧与后来从 MP4 解码出的帧并不完全相同。

应用当前先把嘴部帧编码为有损 MP4，再对内存中的原始嘴部帧做实时推理。因此，历史记录里的 MP4 可以用于查看和回放，但不能完整还原实时推理所用的原始像素。现在还不能仅凭这一个句子断定差异来自压缩影响，也不能据此断定模型一定是唯一原因。

抽查过该 MP4 的画面：共 206 帧、25 fps，嘴部区域可见。它没有显示出明显的空帧或完全裁错，但压缩后细节较软；这只是画面抽查，不等于输入质量已通过完整验收。

## 第一阶段：完成一次可复核样本

下一次录制应同时保存进入识别函数的 96×96 RGB 嘴部帧序列（无损、未经过 MP4 编码）和当前 MP4。之后对这两份输入使用完全相同的 CNVSRC 模型与推理参数；两者都会经过同一套模型输入变换，各重复识别 3 次，并检查：

1. 帧数、尺寸和嘴部画面是否一致、完整；
2. 同一份无损输入重复识别是否每次相同；
3. 无损输入与 MP4 回放的输出及 CER 是否不同。

这一步只诊断输入与回放差异，不训练模型，也不代表个性化适配已经开始。完成后再决定是否值得收集训练素材。

## 一次性采集操作（复现方法）

已在应用加入可选开关。默认启动方式不变；需要采集时，先退出当前 Move Your Lips，再在项目目录 PowerShell 中运行：

```powershell
.\scripts\run_lip_input_mvp.ps1 -SaveLosslessNextInput
```

然后只录一遍上面的原句“我觉得现在的识别结果不准确”。本次实时结果仍会照常识别并保存。无损数组会写入 `outputs/mvp/offline_diagnostic/lossless_inputs/<记录ID>.npz`，MP4 仍写入 `outputs/mvp/recordings/<记录ID>.mp4`。应用启动终端会打印无损文件的完整路径。

拿到这两份文件后，用相同 checkpoint、CPU 和 beam size 10 进行三次重复对照：

```powershell
& 'D:\cnvsrc-env\python.exe' .\scripts\compare_lossless_input.py --reference '我觉得现在的识别结果不准确' --beam-size 10
```

比较脚本默认选择最新的无损文件，并寻找同记录 ID 的 MP4。它会输出两种输入的帧数、像素差异、三次识别文字和 CER。无损文件只采集一条；如需重新采集，需再次带 `-SaveLosslessNextInput` 启动应用。

### 成功配对样本

记录 ID：`70537f62-e6d2-45f6-a2d8-66ae46ade40c`，原句仍为“我觉得现在的识别结果不准确”。应用历史已将这条记录与同 ID 的无损 NPZ 关联；两份输入均为 211 帧、96×96 RGB、25 fps。

| 输入 | 三次离线识别结果 | 三次 CER | 与应用实时结果一致 |
|---|---|---|---|
| 无损原始帧 | 我对的现在的面的结果不是专注力 | 每次 8/13（61.5%） | 是 |
| 从 MP4 解码 | 我对他现在的面的结果不是对的对 | 每次 8/13（61.5%） | 否 |

原始帧三次结果都相同，且与应用当时显示的实时结果逐字一致；MP4 回放的三次结果也相同。这表明两路推理各自可重复。MP4 解码帧与原始帧同尺寸、同帧数；像素平均绝对差为 3.18/255，最大差为 40/255，像素完全相同的比例约 10.6%。画面抽查中，嘴部持续可见且裁剪基本稳定；MP4 稍模糊，没有发现明显漏帧或嘴部裁出画面的迹象。

静态代码核对还确认，应用复用了 CNVSRC 的 `VideoProcess` 嘴部对齐/裁剪实现，并使用 `VideoTransform("test")`：除以 255、中心裁剪至 88×88、灰度化、按均值 0.421 和标准差 0.165 归一化。它与本地 CNVSRC 官方推理变换一致。实时关键点由同仓库的 `LandmarksDetector` 组件逐帧获取。画面和静态代码没有发现明显的裁剪、尺寸、颜色通道或归一化错误；实时帧率重采样方式仍是相对于离线 25 fps 视频的一个小差异，当前没有证据表明它造成了主要错误。

## 本次结论与边界

这次 MP4 压缩改变了部分识别字符，但 CER 没有变化；无损结果仍有 61.5% 字符错误，不能把本次严重错误简单归因于 MP4 保存。结合画面抽查和无损输入重复结果，当前更值得优先查的是 CNVSRC 对这类中文句子的模型/训练数据适配程度，以及整套预处理是否与该 checkpoint 预期一致。单条录制不能证明模型对所有句子都差，也不能证明裁剪和预处理完全正确；它足以说明先前“实时和回放不一致”不能再被用来解释全部识别问题。
