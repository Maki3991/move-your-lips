# Design Thinking 记录：唇语输入法

**文档用途**：记录从问题发现到 Prototype 范围冻结，以及进入 MVP 的思考过程。
**当前阶段**：Define → POV → HMW → Prototype v0.1 固定视频验证 → MVP v0.1 实时交互实现
**状态**：问题和方案仍是个人用户假设；固定视频技术链路已跑通但质量验收未通过，当前进入实时摄像头 MVP，先验证产品闭环是否成立。
**最后更新**：2026-10-11

这不是 PRD，也不是 Design Thinking 教材。它只记录本项目为什么这样定义问题、为什么选择当前方向，以及哪些地方仍然没有证据。

## 1. 记录规则

每个判断都尽量标记为：

- **事实**：我亲自观察到、运行过或留下了可检查记录的内容。
- **假设**：目前合理，但还没有被外部行为或实验验证。
- **决策**：在多个选项中主动选择了一个方向。
- **待验证**：需要通过 Prototype、测试或后续用户反馈回答的问题。

当前最重要的边界是：我可以从自己的真实体验开始，但不能把个人体验直接写成“所有用户都有这个问题”。

## 2. 起点：我观察到的问题

### 事实：User 0 的真实体验

- 我重度依赖语音输入法，每天有十次以上与 AI 沟通的需求。
- 我经常使用 AI 工具进行思路梳理、复杂解释和较长内容输入。
- 在教室、图书馆等不能出声的场合，我不能自然使用语音输入。
- 改用键盘输入后，速度下降，思路容易被打断，新的想法可能在输入过程中消失。
- 为了继续使用语音输入，我有时会拿着手机离开电脑，到外面说完后再回来继续工作。
- 我希望第一版先为自己设计，并把自己作为这一类用户的第一个样本。

### 当前替代方式

- 手动键盘输入。
- 拿手机离开电脑，在外面使用语音输入或远程操作。
- 等到可以讲话的环境再输入。
- 使用目前尚未验证、且成本较高的隐私/隔音方案。

### 尚未证明的推断

- 其他重度语音输入用户也会频繁遇到相同问题。
- 他们愿意把脸对着摄像头，并接受识别错误和修正成本。
- 唇语输入的总耗时会低于键盘输入加修正。

## 3. 5W1H 问题展开

| 问题 | 当前回答 | 状态 |
| --- | --- | --- |
| Who：谁 | 首先是我自己；未来可能是重度语音输入的中文用户 | 部分是假设 |
| What：要完成什么 | 在不发出声音的情况下，把连续想法转换成中文文本，未来用于向 AI 输入 | 初步明确 |
| When：什么时候 | 不能或不方便出声，但仍需要在电脑前工作时 | User 0 事实 |
| Where：在哪里 | 第一版限定为教室等相对空旷、摄像头画面中只有本人的共享环境 | Prototype 决策 |
| Why：为什么痛苦 | 语音输入被迫停止，键盘输入变慢并打断思路 | 初步洞察 |
| How：现在怎么做 | 键盘输入、延后输入或放弃较长表达 | User 0 观察 |

## 4. 当前的 Problem Statement

> 当我在教室等共享环境中需要和 AI 沟通时，出声输入会让别人听见或打扰别人，因此我无法使用最习惯的语音输入；改用键盘后，输入速度跟不上思考速度，导致思路被打断、想法丢失，甚至必须离开电脑、转用手机完成沟通。

这句话目前是**问题假设**，不是市场结论。

### 问题边界

我们要解决的是：公共场合中的无声中文长文本输入。

我们暂时不声称解决：

- 所有人的通用中文输入。
- 连续自然对话或系统级输入法替代。
- 侧脸、遮挡、昏暗环境和多人场景下的鲁棒识别。
- 商业可用的中文唇语基础模型训练。

## 5. POV（Point of View）

> 作为一个每天多次依赖语音输入与 AI 沟通的学生，我需要在教室等只有自己处于摄像头画面中的共享环境里，以不发出声音、不打扰他人的方式，把连续的想法转换成中文文本，因为键盘输入会打断我的思考，而离开电脑使用手机又会破坏我的工作流程。

POV 的作用不是证明唇语是唯一答案，而是明确：用户、场景、任务、痛点和后果。

## 6. HMW（How Might We）

> 我们如何帮助像我这样依赖语音输入的用户，在教室等共享环境中不发出声音、不打扰他人的情况下，仍然以接近语音输入的效率，把连续想法转换成可用的中文文本？

这个 HMW 暂时不把“摄像头唇语识别”写进问题本身，以免把解决方案伪装成问题定义。

## 7. 方案选择记录

目前知道或考虑过的方向：

| 方向 | 解决什么 | 当前判断 |
| --- | --- | --- |
| 隔音口罩 + 内置麦克风 | 保留语音输入，但减少外部声音 | 需要硬件、佩戴和隐私验证 |
| 摄像头唇语输入 | 不发出声音，通过视觉动作生成文本 | 本项目当前主方向，仍需验证可行性 |
| 继续键盘输入/快捷短语 | 不增加新硬件 | 是当前基线和对照方案 |

### 当前决策

先验证摄像头唇语输入是否能为 User 0 产生有用的中文草稿。选择它的原因是：它直接对应“不能发声但仍想使用语音式表达”的需求，并且可以先复用公开模型，不必从零训练。

## 8. Prototype 的目的

Prototype 不是“把完整产品做小一点”，而是用低成本回答一个关键问题。

### 本轮最关键的问题

> 由 User 0 录制的一段、正面、稳定光线的无声普通话视频，能否在本机被转换成基本可用的简体中文文本？

### Prototype v0.1：固定视频识别

本轮只验证下面这条链路：

```text
选择固定视频 -> 读取视频画面 -> 中文视觉语音识别 -> 显示文本结果
```

输入条件：

- 5 段由 User 0 录制的普通话视频；
- 每段不超过约 10 秒；
- 正面机位、稳定光线、单人画面；
- 视频不提供可供模型使用的音频信息；
- 每段视频配套一份人工确认的标准答案文本。

最小用户流：

1. 选择一段测试视频；
2. 运行识别；
3. 查看识别结果；
4. 对照标准答案；
5. 记录识别效果、运行时间和失败原因。

### 本轮明确不做

- 实时摄像头采集；
- Alt 等开始/结束快捷键；
- 输入框自动填充；
- 系统级输入法；
- AI 润色、总结、改写或意图理解；
- 多人、拥挤背景、侧脸、遮挡和复杂光线。

这些功能属于后续阶段。当前先把模型输入、推理和文字输出这条最小链路跑通。

### 本轮验收边界

P0 只需要证明：

- 视频能够被系统读取；
- 模型能够完成一次推理；
- 系统能够显示文字结果；
- 结果能够与标准答案进行比较；
- 失败时能够留下可复查记录。

### 当前验证结果

已使用一段手机录制的无声视频完成一次 CNVSRC2025 baseline 冒烟测试：

```text
全脸视频 -> RetinaFace/FAN -> 96×96、25 FPS 嘴部视频 -> CNVSRC2025 -> 中文文本
```

这证明的是“本机技术链路能够运行”，不等于“唇语输入已经可用”。初始版本错误地把 30 FPS 视频直接标记为 25 FPS，得到 52.94% CER；修正为真正的 30→25 FPS 重采样后，模型输出为“你好我想用说剧组和人工智能聊天”，目标为“你好我想用唇语输入法和人工智能聊天”，CER 降为 29.41%，但质量验收仍失败。当时的下一步是做官方样例对照；随后新闻播音员基准也未通过，因此项目先停止继续扩展同一模型的离线测试，转而验证原始产品闭环。

5 段视频只能作为原型冒烟测试，不能据此宣称模型已经达到稳定的 80% 准确率，也不能据此证明其他用户已经被验证。

## 9. 从 Prototype 进入 MVP 的决策

固定视频 Prototype 已回答“模型链路能否在本机运行”，但没有回答原始产品问题：用户能否在电脑前不出声、无需手机和视频搬运，直接完成一次唇语输入。因此本项目不再把“准确率达到可用标准”作为进入实时交互开发的前置条件，而把它作为 MVP 中单独记录和迭代的指标。

### 当前 MVP 要验证的关键假设

> 如果用户能通过一个快捷键控制摄像头录制，并在结束后得到一次中文识别结果复制到剪贴板，那么即使当前识别准确率有限，也能先验证“摄像头唇语输入”的基本交互闭环是否成立。

### MVP v0.1 的最小用户流

```text
启动程序 -> 介绍页（摄像头关闭） -> 按住 F9 -> 启动摄像头
-> 显示嘴部裁剪和实时识别 -> 松开 F9 -> 关闭摄像头
-> 等待最终识别 -> 结果复制到剪贴板
```

### MVP v0.1 In scope

- 启动时不占用摄像头，按住 F9 后才打开摄像头；
- 单人、正面、稳定光线下的本地摄像头采集；
- F9 按下/松开控制一次录制；
- 嘴部主体及少量周边的固定裁剪窗口；
- 裁剪窗口上方的录制提示、下方的实时识别和松开后的识别状态；
- 复用 CNVSRC2025 完成中文识别；
- 识别完成后复制结果到剪贴板；
- 记录帧数、识别耗时、错误和结果，供后续评估。

### MVP v0.1 Out of scope

- 自动粘贴到任意输入框或系统级输入法；
- 麦克风、音频输入、外部 LLM 润色或改写；
- 多人、侧脸、遮挡、拥挤背景和复杂光线；
- 重新训练模型、个人微调和准确率承诺。

具体功能需求、异常状态和验收条件见 [`docs/mvp-prd.md`](mvp-prd.md)。当前代码已经进入实现，但摄像头实测、快捷键实测和端到端用户验收仍属于待验证证据。
